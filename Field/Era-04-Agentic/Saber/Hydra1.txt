## The architecture

There are three layers:

1. **PROSDK core** — runtime, networking, authentication, platform abstraction, logging, telemetry, and generic backend services.
2. **Hydra 5 services** — game-specific multiplayer, social, persistence, economy, and dedicated-server APIs.
3. **Unreal adapters** — Blueprint-visible enum equivalents and conversion functions.

The exported functions use C linkage, but the interface uses C++ features such as scoped enums, default member values, and default arguments. Treat it as a **C++ SDK with a stable C ABI**, not a C-compatible SDK.

The version is `5.19.8.248-ms26.3.3.204`, built June 15, 2026, with interface signature `0xcac400`; that signature presumably protects against linking incompatible headers and binaries. See [prosdk.h](./sdk/prosdk.h:4).

## Expected client lifecycle

Conceptually, a game integration does this:

```text
optional platform/runtime configuration
        ↓
prosdk_init(...)
        ↓
create one PROSDK_AUTH_HANDLER per local user
        ↓
register authorization state callback
        ↓
connect using Steam / PSN / Xbox / EOS / Nintendo / developer login / etc.
        ↓
wait for ONLINE while regularly calling prosdk_update()
        ↓
subscribe to and use Hydra services
        ↓
disconnect users/services
        ↓
continue updates until settled
        ↓
prosdk_term()
```

The core lifecycle functions are in [prosdk.h](./sdk/prosdk.h:69), while platform authentication methods are in [prosdk_authorization.h](./sdk/prosdk_authorization.h:44).

Multiple local users are supported: each gets an opaque `PROSDK_AUTH_HANDLER`. Almost every user-facing call receives that handle.

## Service map

The generic `prosdk_*` layer provides:

- Platform authorization and account linking
- Agreements, entitlements, banners
- Cross-save
- Mods and container upload/download
- Leaderboards
- Telemetry and backend “facts” logging
- Time-limited events
- Profanity filtering
- HTTP and file caching
- Custom allocation and filesystem callbacks

The `hydra5_*` user layer provides:

- Parties, invitations, and join codes
- Matchmaking queues and game sessions
- Crossplay modes, teams, roles, and session browsing
- TURN relay acquisition
- Friends and recent players
- Presence
- Messaging and signaling
- Economy and offers
- Challenges and ratings
- Privacy, bans, and reports
- Game configuration
- Arbitrary versioned binary data containers
- Standalone server browsing
- Session-control handshakes

The server layer supports two primary models:

- **Heated/managed servers:** backend or DSM-provisioned, activated after authorization, with explicit client acceptance and session state.
- **Standalone servers:** user-issued short-code login, server browser metadata, filters, properties, and configurable token lifetime.

The managed server lifecycle is especially stateful: sign in, wait for `READY_TO_ACTIVATE`, obtain activation data, activate, then accept or reject connecting clients. See [hydra5_sdk_server_authorization_simple.h](./sdk/hydra5/hydra5_sdk_server_authorization_simple.h:88).

## Matchmaking is the center of gravity

The most substantial API area is presence/matchmaking. It models:

- Party state separately from game-session state
- Queueing and explicit session creation
- Pending acceptance
- Session ownership, teams, class roles, variants, and member data
- Crossplay search and session categories
- Public session browsing
- Join-in-progress
- Penalties
- Relay/TURN data

Long matchmaking operations are mutually exclusive. An immediate `SUCCESS` generally means the request was accepted; the authoritative result arrives later through a callback or state update. Some mutations explicitly say that their completion callback does **not** mean the new state has propagated yet. See [hydra5_sdk_user_service_presence_matchmaking.h](./sdk/hydra5/hydra5_sdk_user_service_presence_matchmaking.h:229).

That suggests the Unreal wrapper should expose matchmaking as a state machine, not as isolated Blueprint functions returning booleans.

## Memory and callback semantics

This is the main integration hazard.

The API uses several ownership models:

- Result valid only during the callback: copy it immediately.
- Result allocated by the SDK: call the matching `*_release()` function.
- Cached snapshot returned synchronously: often still requires an SDK release.
- Input pointers: likely need to remain valid until request ingestion, but the headers do not consistently state whether they are copied immediately.

A wrapper should immediately convert SDK results into Unreal-owned `FString`, `TArray`, and `USTRUCT` values, then release the SDK memory. Raw SDK pointers should not escape the adapter layer.

Also watch for `SDK_ALL_DATA_READY_ALREADY`: it is non-fatal and can mean that **the callback will never execute**. A generic async wrapper must resolve the operation immediately in that case.

## Unreal-generated portion

Each generated enum typically has:

- The native SDK enum.
- A `_ue.h` Blueprint-facing `UENUM`.
- An `.impl.h` pair of native ↔ Unreal conversion specializations.

For example:

- [hydra5_autogen_presence_enums_ue.h](./sdk/autogenerated/unreal/hydra5_autogen_presence_enums_ue.h:3)
- [hydra5_autogen_presence_enums.impl.h](./sdk/autogenerated/unreal/hydra5_autogen_presence_enums.impl.h:6)

The referenced `.generated.h` files are intentionally absent; Unreal Header Tool creates those during the plugin build.

There is no Hydra umbrella header. Plugin code will need either:

- Explicit service includes, or
- A plugin-owned internal umbrella header.

Also, `prosdk.h` includes only a subset of generic services, so it should not be assumed to expose everything.

### Account service

[Account.h](./Plugin/Public/Services/Account.h) exposes both Blueprint and native delegate surfaces.

Its flow is:

1. `Connect(LocalUserNum)` resolves the user’s authorization handle and subscribes to account-link state changes.
2. `RequestQRLink()` asks the SDK for QR data asynchronously.
3. The callback calls `OnAccountGetLinkDone()`.
4. That reads the SDK’s cached account status.
5. The status is copied into Unreal-owned data.
6. QR data is broadcast to Blueprint and C++ listeners.
7. An Unreal timer requests a replacement when the QR code expires.
8. Link-state changes are broadcast independently.
9. `GetStatus()` exposes the current cached snapshot.
10. `TryToFetchStatus()` requests backend synchronization.

[AccountData.cpp](./Plugin/Services/AccountData.cpp) performs deep SDK→UE conversion:

- `const char*` → `FString`
- PNG buffer → `TArray<uint8>`
- Native enums → Blueprint enums
- Nested SDK records → nested `USTRUCT`s

The SDK status object is released after conversion, so UE-facing values remain self-contained.

All actual `prosdk_account_*` calls used by the implementation exist in the supplied SDK. The apparent `prosdk_account_get_link` occurrence is only an outdated log message.
